# 设计决策：历史查看「冻结」及其代价

## 决策

本系统对**已经完成的查看实行冻结**：

- 每次查看一旦写入，其信息时点 t_k、Z 统计量、停止边界 ±c_k、
  累计消耗 α\*(t_k)、结论（继续 / 拒绝 H0 / 反向拒绝）全部固化为不可变快照；
- 之后推送方对历史批次发来的更正，只进入**当前累计值**和**后续查看**，
  绝不回溯修改任何一行查看记录，也不改变后续边界所依赖的历史时点序列；
- 实验一旦曾越过边界，`concluded` 标志保持为真；但收到更正/新数据后
  **仍然允许继续查看**（历史结论冻结 ≠ 禁止再观测）。若更正后的 Z 回到界内，
  接口响应与页面会给出醒目提示：

  > 「实验曾在第 k 次查看越过边界并宣布结论；更正后的当前统计量未越过本次
  > 边界。历史结论按冻结策略保留不改写，但当前证据已不再支持该结论……」

- 更正使原始信息比例倒退时，有效 t 被夹在上一次有效 t 上（单调不减），
  并置 `clipped=true`、在警告信息中给出 raw 值；
- 同一信息时点（样本量没变、只改了转化数）允许再次查看：该次查看不增加
  信息、不新消耗 α，边界沿用上次值，按新 Z 判定。

数据库层：`batches` 表保存每个批次号的**最新值**，`batch_events` 表保存
**不可变事件流**（insert / correction / duplicate_ignored 三态，含更正前后
数值）。冻结的查看在 `looks` 表中没有任何 UPDATE 路径（应用层只 INSERT，
`perform_look` 不加载可变聚合以外的历史字段）。

## 为什么是冻结而不是重算

另一种方案是「不冻结」：每次更正后重算全部历史查看，边界和已宣布结论
都可能被改写。它的代价在题目场景里是不可接受的：

1. **产品同学第九天已经"宣布胜出、全量上线"。** 一个两周后可能把
   reject 改写成 continue 的系统，等于让历史决策失去依据；线上已经放量的
   事实无法回滚，报表却显示"当时并未显著"，审计上无法自洽。
2. 重算方案下，**每一次更正都会改变 α 消耗轨迹**（历史 t 变了，后续所有
   边界跟着变），监控人员面对的是一条会"自己移动"的停止线，停止规则不再
   是预先承诺（pre-registered）的规则，对第一类错误的控制承诺随之失效。
3. 冻结方案下，整体 I 类错误控制严格建立在**实际发生的（冻结）查看时点**上，
   事后无法被数据更新操纵，符合成组序贯方法的标准使用规范。

## 冻结的代价（明确列出，不回避）

1. **更正后，已宣布结论可能与当前数据矛盾。** 例如埋点重复计数导致虚高，
   更正后真实 Z 回到界内；历史 reject 不会被撤回，系统只能显著提示，
   **是否下线/回滚的决策权和责任在人**，系统不替人翻案。
2. **当前累计值与历史轨迹之间可能出现"跳变"。** 轨迹图中 Z 点基于当时
   冻结的快照，不代表用最新数据重算的结果；页面通过更正标记、警告横幅、
   事件流中前后值对照三处提示，避免误读。
3. **信息时间被夹断会略微保守。** 更正使样本量缩小时，有效 t 不后退，
   后续边界按"信息已经走了这么远"计算，末期停止线会略低一点点；这只会让
   检验更保守（更难显著），不会抬高第一类错误，但可能损失少量功效。
4. 冻结的只是**统计结论**；批次的最新值仍然更新，审计者既能看到
   「当时基于什么数据宣布了什么」，也能看到「现在数据被改成了什么」。

## 页面上的更正提示（三处）

- 手动查看响应中的 `correction_warning`：详情页顶部黄色横幅，明确说明
  冻结语义、信息时间倒退夹断、以及（若发生）证据反转；
- 查看记录表：`含更正` 徽标 + `截断/夹断` 徽标，历史行不可编辑；
- 「推送/更正事件」标签页：每条更正都显示旧值→新值、批次号、时间戳。

## 幂等与批次规则

- 同批次号 + 完全相同的四元组再次推送：HTTP 200，`status=duplicate_ignored`，
  仅追加一条事件，累计值不变（推送方可安全重试）；
- 同批次号 + 不同内容且未声明更正：HTTP 409，字段级标出
  `batch_no` / `is_correction`，拒绝写入；
- 对不存在的批次声明更正：HTTP 409，标出 `batch_no`；
- 推给不存在的实验：HTTP 404。

## 确定性与重启恢复

所有进入边界计算的输入都持久化在 PostgreSQL 16：

- `experiments`：α、功效、计划样本量 N；
- `batch_events`：定义重放顺序的不可变事件流（自增主键 id）；
- `looks`：每次查看冻结的全部输入输出，含 `based_on_event_id`
  （触发时最新事件 id）与 `prior_info_times_json`。

重放接口 `/api/experiments/{id}/replay` 按事件 id 顺序重建内存批次表，
在每个 `based_on_event_id` 处用同一算法重算，与在线快照逐字段比对
（容差见 `docs/statistics.md` 第 5 节）。重启后因为只是重新加载同样的
持久化输入，状态与边界完全一致。
